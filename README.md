# OKK 自用源

每天凌晨自动清洗一遍，只留能播的。手工维护的部分放在 `source/`，根目录的 `tv.m3u` 是机器生成的，别手改。

## 订阅地址

```
https://raw.githubusercontent.com/Zoramartina/OKK/main/tv.m3u
```

raw 直连不稳的话套镜像：

```
https://gh-proxy.com/https://raw.githubusercontent.com/Zoramartina/OKK/main/tv.m3u
```

## 目录

| 路径 | 说明 |
| --- | --- |
| `source/` | **手工维护区**，改了这里才算数 |
| `tv.m3u` | 自动生成，只含 `source/` 里挑出来的源，订阅用的就是它 |
| `dist/all.m3u` | 主源 + 自动搜集的合并版 |
| `dist/cctv.m3u` `weishi.m3u` `gangao.m3u` `difang.m3u` | 分类版 |
| `dist/report.md` | 每次清洗的报告：剔了哪些、为什么剔 |
| `dist/detail.tsv` | 逐条明细，含响应时间、速度、失败原因，方便自己翻 |

## 怎么加源

两种方式。

**手工加**：在 `source/` 下的 txt 或 m3u 里加一行 `频道名,地址`，提交，工作流会自动跑一遍。格式见 `source/README.md`。

**让机器自己找**：`config.json` 里的 `remote` 是一组每日拉取的公开源地址，清洗时和手工源合在一起验证，结果进 `dist/all.m3u`。想加新的直接往数组里加地址。

## 每天的活

GitHub Actions 每天北京时间 03:00 跑：

1. 读 `source/` 里所有源
2. 拉 `remote` 的补充源
3. 逐条探测：先拿 m3u8，再往下追到分片真下到数据才算通过
4. 失败的剔除，IPv6 源和反盗链的保留但标注
5. 重写 `tv.m3u` 和 `dist/`，自动提交

手动触发：Actions 页 → 清理直播源 → Run workflow。

## 两条要注意的

**`http-user-agent` 会被保留**。原文件里 42 条源靠这个属性能播，清洗时会按各自的 UA 去探测，不会误杀。

**主源的线路不会被砍**。同一个频道留多少条线路由你手工决定，脚本不清洗这块。自动搜集来的源才会限制每频道最多 3 条（`config.json` 里的 `max_per_channel`）。

## 判定为什么是三档

IP 段被限流是这套东西最大的坑。实测同一个地址，单独串行访问返回 200，放在几千条一起跑的时候返回 403——这台机器一轮扫下来，约三分之一会撞上 403。

所以判定分三档，只有明确死亡才会删：

| 档位 | 依据 | 处理 |
| --- | --- | --- |
| 通过 | 拿到 m3u8，追到分片真读到了数据，且列表还在前进 | 保留，排前面 |
| 存疑 | 403/429、IPv6 源、域名解析失败、反盗链挡住分片、**播放列表停滞** | **保留**，排在后面，`report.md` 里标原因 |
| 死亡 | 404、连接被拒、超时、TLS 握手失败、返回 HTML 错误页 | 删除 |

403 不删是踩过坑之后的决定：抽 10 个不同宿主复查，5 个实际能通。宁可留几条不播的，也不把能播的删掉。

**播放列表停滞**是单独一档。有些源分片能正常下载，但 m3u8 里的媒体序列号长时间不前进，播放器就会把那几十秒画面无限循环——看起来像在播，其实内容早就卡死了。所以跑完一轮会隔 90 秒再抓一次列表，序列号没动就标成“循环回放”。2026 年 1 月起中国蓝（cztv）那批 lantian 源全挂成这个样子，就是靠这条检测抓出来的。
